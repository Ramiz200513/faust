## 1. Что делает релей

Пять обязанностей (они же перечислены в javadoc `JarvisWebSocketHandler`):

1. **Аутентификация.** Первое сообщение в сокете — `auth` (или `pair_request`). Без успешного входа ничего другого не принимается.
2. **Маршрутизация.** Команды телефона → нужному агенту; результаты, кадры, шаги, **вопросы и планы** агента → всем телефонам этого ПК.
3. **Понимание фраз.** `nl` («сделай потише») → конкретная команда. Первой отвечает **своя модель** (Ollama на этом же ПК), при сомнении — Gemini, без интернета — правила по ключевым словам.
4. **Белый список.** Всё, что не разрешено, не дойдёт до агента, даже если это «придумал» ИИ. Плюс **запрет опасных целей** у задачи агенту.
5. **Аудит.** Каждая команда → строка в таблице `audit_log`.

Плюс вспомогательные вещи по HTTP: выдача одноразовых кодов привязки, **прокси к Gemini для агента** (чтобы ключ ИИ жил только здесь) и три служебных эндпоинта под админским секретом — для сбора обучающих данных, замера точности и выгрузки «уроков».

И ещё одна тихая обязанность: релей следит, **чем кончилась команда**. Если фразу понял только Gemini и агент выполнил её успешно, фраза становится подтверждённым «уроком» для своей модели (раздел 10.5).

## 3. Минимум Spring Boot, чтобы читать код

| Понятие | Смысл | Пример |
|---|---|---|
| **Бин (bean)** | Объект, который создаёт и хранит Spring. Обычно один на всё приложение | `CommandWhitelist`, `DeviceAuthService` |
| **`@Component` / `@Service` / `@RestController` / `@Configuration`** | «Spring, создай этот класс как бин». Разница — только смысловая | `@Service class PairingService` |
| **Внедрение зависимостей (DI)** | Spring сам передаёт нужные бины в конструктор | `JarvisWebSocketHandler(ObjectMapper, CommandWhitelist, IntentParser, …)` |
| **`@Primary`** | Если бинов одного интерфейса несколько — брать этот | `IntentParser` реализуют три класса; `@Primary` стоит на `HybridIntentParser` — его и получает обработчик сокета |
| **`@Value("${ключ:дефолт}")`** | Подставить настройку из `application.yml` / переменной окружения | `@Value("${jarvis.admin-token}")` |
| **`@Bean`** | Метод в `@Configuration`, возвращающий бин | `passwordEncoder()` → `BCryptPasswordEncoder` |
| **`@RestController` + `@PostMapping`** | HTTP-эндпоинт; возвращаемый объект → JSON | `POST /api/pairing-codes` |
| **`ResponseEntity`** | Ответ с явным HTTP-кодом | `ResponseEntity.status(401).body(...)` |
| **`@Entity`** | Класс ↔ таблица БД | `Device` ↔ `devices` |
| **`JpaRepository<T, ID>`** | Интерфейс; Spring **сам пишет реализацию** (`save`, `findById`…) и даже SQL по имени метода (`findByAgentId`) | `PhoneBindingRepository` |
| **`@Transactional`** | Все операции с БД в методе — одна транзакция: либо всё, либо ничего | `DeviceAuthService.authenticate` |
| **`record`** (Java 16+) | Короткий неизменяемый класс с полями, конструктором, `equals`, геттерами `x()` | `JarvisMessage.Auth` |
| **`sealed interface … permits`** (Java 17) | Закрытое семейство, как в Kotlin | `Command` |
| **`switch` по типу** (Java 21) | `case JarvisMessage.Ping p -> …` | в `handleTextMessage` |

## 4. Запуск: Docker, compose, .env, application.yml

### 4.1 `Dockerfile` — двухэтапная сборка

```
Стадия 1 "build":  eclipse-temurin:21-jdk
   COPY gradlew, gradle/, build.gradle.kts, settings.gradle.kts
   RUN ./gradlew --version          ← слой с Gradle кэшируется, пока не менялись файлы сборки
   COPY src
   RUN ./gradlew bootJar            ← один «толстый» jar со всеми зависимостями
Стадия 2 "run":    eclipse-temurin:21-jre   (только JRE, без компилятора — меньше и безопаснее)
   COPY --from=build .../*.jar app.jar
   useradd relay; USER relay        ← не от root
   ENTRYPOINT java -jar app.jar
```

Почему два этапа: инструменты сборки (JDK, Gradle, исходники) в итоговый образ не попадают.

`.dockerignore` исключает `build/`, `.gradle/`, `docs/`, `scripts/`, `.env` — быстрее сборка и секреты не попадут в образ.

#### `Dockerfile.local` — быстрый путь

У честной сборки внутри Docker есть цена: при сброшенном кэше Docker заново качает из интернета Gradle и все библиотеки (~0,5 ГБ). 2 октября на медленной сети это заняло больше 10 минут. На ПК разработчика всё это уже лежит в кэше Gradle, поэтому появился второй файл:

```
FROM eclipse-temurin:21-jre
COPY app.jar app.jar          ← jar уже собран Gradle на самом компьютере
useradd relay; USER relay     ← не от root, как и в основном
ENTRYPOINT java -jar app.jar
```

Им пользуется `faust.ps1` (функция `Build-RelayLocally`): `gradlew.bat bootJar` → jar копируется в `build/docker-local/app.jar` (отдельная папка-контекст, потому что `.dockerignore` исключает `build/` целиком) → `docker build -f Dockerfile.local -t jarvis-relay-relay:latest build\docker-local`. Интернет не нужен, вся пересборка — около минуты. Если локальная сборка не удалась (нет Java, сломан кэш), скрипт сам возвращается к основному `Dockerfile`. На защите это значит: пересборка релея не зависит от сети в аудитории.

### 4.2 `docker-compose.yml` — два сервиса

| Сервис | Образ | Порт | Особенности |
|---|---|---|---|
| `postgres` (контейнер `jarvis-relay-db`) | `postgres:16-alpine` | 5432 | Том `jarvis-db-data` — данные переживают перезапуск; healthcheck `pg_isready` |
| `relay` (контейнер `jarvis-relay`) | собирается из `Dockerfile` | 8080 | `depends_on: postgres: condition: service_healthy` — ждёт готовности базы; healthcheck — слушает ли порт 8080 (через `/dev/tcp` bash, без curl) |

У обоих `restart: unless-stopped` → поднимаются сами после перезапуска Docker/Windows.

Внутри Docker-сети релей обращается к базе по имени сервиса: `jdbc:postgresql://postgres:5432/jarvis`.

**Как контейнер видит Ollama.** Своя модель работает в Ollama **на самом компьютере**, а не в контейнере (ей нужна видеокарта). Из контейнера `localhost` — это сам контейнер, поэтому адрес модели — `http://host.docker.internal:11434`. Docker Desktop знает это имя сам; строка `extra_hosts: "host.docker.internal:host-gateway"` в compose нужна, чтобы то же работало на Linux-сервере.

Шесть последних переменных в `.env.example` пока **не вписаны** — они работают по значениям по умолчанию из `docker-compose.yml` и `application.yml`. Чтобы поменять, достаточно дописать строку в `.env`.

`faust.ps1` при запуске сам выставляет `JARVIS_OPEN_REGISTRATION=true` (переменная окружения важнее файла) — чтобы ПК подключался кнопкой «Подключить» без кода от администратора. Для дома это то, что нужно; на публичном сервере релей так запускать не стоит.

  datasource: url/username/password из JARVIS_DB_*
  jpa.hibernate.ddl-auto: update     # Hibernate сам создаёт/дополняет таблицы по сущностям

```

Синтаксис `${ИМЯ:дефолт}` — взять переменную окружения, а если её нет — дефолт.

`ddl-auto: update` — удобно для MVP: схема подстраивается под Java-классы. Для продакшена нужны явные миграции (Flyway/Liquibase) — `update` не удаляет колонки и может «молча» делать неожиданное.

### 4.5 Режимы запуска

- **Каждый день:** `C:\diplom\start-faust.bat start` — поднимет Docker, базу, релей, проверит Ollama, запустит агента. Сам сравнивает время изменения исходников со временем сборки образа и пересобирает релей только если код менялся.
- **Вручную:** `docker compose up -d --wait --build` — всё в Docker.
- **Разработка:** `docker compose up -d postgres --wait` + `./gradlew bootRun` — релей процессом на хосте, быстрее цикл правок. (В этом режиме адрес Ollama — `http://127.0.0.1:11434`, а не `host.docker.internal`.)

**Помни:** `gradlew compileJava` контейнер **не обновляет**. Правка кода → `start-faust.bat start` или `docker compose up -d --build`.

## 5. Протокол на Java

Пакет `protocol/` — зеркало Kotlin-протокола из `jarvis/shared`. Точно такая же копия лежит в агенте.

### Как Jackson понимает `"type"`

```java
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, include = JsonTypeInfo.As.PROPERTY, property = "type")
@JsonSubTypes({
    @JsonSubTypes.Type(value = JarvisMessage.Auth.class, name = "auth"),
    @JsonSubTypes.Type(value = JarvisMessage.AuthResult.class, name = "auth_result"),
    ...
})
public sealed interface JarvisMessage permits ... {
    String requestId();
    record Auth(String requestId, String deviceId, String token, DeviceRole role, int protocolVersion) implements JarvisMessage {}
    ...
}
```

`@JsonTypeInfo` говорит: «при чтении посмотри поле `type` и по таблице `@JsonSubTypes` выбери класс». При записи Jackson сам добавит `"type":"auth"`. Это полный аналог `classDiscriminator = "type"` в Kotlin.

Enum-значения задаются `@JsonProperty("phone")` — чтобы в JSON было `"phone"`, а не `"PHONE"`.

Классы: `JarvisMessage` (12 видов сообщений + вложенные `PlanItem` и `PlanItemStatus`), `Command` (24 команды, у каждой метод `name()`), `ResultData` (5 видов данных + вспомогательные `ProcessInfo`, `FileEntry`), `CommandStatus`, `DeviceRole`, `ImageFormat`, `AgentScope`.

Добавлено 30 сентября: сообщения `agent_question` (вопрос ИИ-агента человеку) и `agent_plan` (план многоэтапной задачи), команды `answer_question` (ответ на вопрос) и `set_display_option` (что показывать на экране ПК). Релей в их смысл не вникает: сообщения пересылает телефонам, команды проверяет белым списком и отдаёт агенту. `AgentQuestionProtocolTest` проверяет, что вопрос и план проходят через релей **без потери полей**.

### Главная ловушка

Релей **десериализует** сообщение агента в свой Java-класс и **сериализует заново** перед отправкой телефону. Значит, если в Kotlin и в агенте добавили поле, а в релее — нет, **релей молча его выбросит**. Так и случилось с `screenWidth/screenHeight` в `ScreenFrame` — тапы по экрану промахивались. Отсюда инвариант: протокол меняется **синхронно в трёх местах**.

С новым **типом** сообщения хуже, чем с новым полем: Jackson не найдёт `"type":"agent_question"` в таблице `@JsonSubTypes` и бросит исключение на разборе. Поэтому релей, собранный до 30 сентября, с новым агентом несовместим — их обновляют вместе. Так и вышло 30.09: Docker после холодного старта не сразу отдал сведения о контейнере, скрипт решил «не знаю — не пересобираю» и поднял старый образ. С тех пор `faust.ps1` делает несколько попыток `docker inspect`.

`protocolVersion` в `Auth` приходит, но релей его **не проверяет** — поле зарезервировано на будущее.

## 6. WebSocket: сердце релея

### 6.1 `WebSocketConfig.java`

```java
registry.addHandler(handler, "/ws").setAllowedOrigins("*");
```

Адрес подключения: `ws://<хост>:8080/ws`. Буфер текстового сообщения поднят до **8 МБ** (по умолчанию у Spring 8 КБ — скриншот в base64 «рвал» соединение). Таймаут простоя — 10 минут.

### 6.2 `SessionRegistry.java` — кто на связи

```java
Map<String, WebSocketSession> agents   // id агента -> его сокет
Map<String, PhoneEntry>       phones   // id сокета телефона -> (сокет, targetAgentId)
Set<String> streamingAgents            // кто сейчас стримит экран
```

`ConcurrentHashMap` — колбэки WebSocket приходят из разных потоков.

| Метод | Что делает |
|---|---|
| `registerAgent(agentId, session)` | Запомнить сокет агента (новый вытесняет старый) |
| `registerPhone(session, targetAgentId)` | Запомнить телефон и его ПК |
| `remove(session)` | Убрать закрытый сокет. Сравнение **по id сокета**, а не по agentId: если агент уже переподключился, новый сокет не тронем |
| `agentFor(targetAgentId)` | Сокет нужного агента. `targetAgentId == null` (старая схема) → никто; **любой** живой агент — только при `jarvis.legacy-phones.enabled=true` |
| `isAgentOnline(id)` | Для `agentOnline` в `auth_result` |
| `phonesOf(agentId)` | Телефоны этого ПК (+ телефоны старой схемы, если она включена) — им пересылаются результаты |

> **Почему старая схема выключена (30.10).** Телефон без конкретного ПК получал бы кадры экрана, шаги и вопросы **всех** агентов релея и командовал бы первым попавшимся. Пока ПК один, это незаметно; при нескольких ПК — прямая утечка. Теперь по умолчанию такой телефон не проходит Auth («привяжите ПК заново по QR-коду»), а реестр не выдаёт ему ни агента, ни чужих сообщений. Проверка — `SessionIsolationTest`.
| `setStreaming / isStreaming` | Учёт стримов (сейчас только записывается) |

Реестр живёт **в памяти**: перезапуск релея = все переподключаются (клиенты делают это сами).

### 6.3 `JarvisWebSocketHandler.java` — вся логика сообщений

Наследует `TextWebSocketHandler`; Spring вызывает `handleTextMessage` на каждое сообщение и `afterConnectionClosed` при закрытии.

```
handleTextMessage(session, text):
    msg = Jackson.readValue(text, JarvisMessage.class)
    role = session.attributes["role"]
    if role == null:                         ← ещё не вошёл
        msg is PairRequest ? handlePair : handleAuth
        return
    switch (msg):
        Ping           -> отправить Pong
        CommandRequest -> handleCommand
        CommandResult  -> если от агента: status OK ? lessons.confirm(requestId)
                                                    : lessons.reject(requestId)
                          затем forwardToPhones
        ScreenFrame | AgentStep | AgentQuestion | AgentPlan -> forwardToPhones
        default        -> warning в лог
```

Новое в этой развилке — строка про `lessons`: итог выполнения команды заодно служит проверкой «урока» для своей модели. Фразу, которую понял только Gemini, релей запоминает **лишь если команда удалась** (подробно — 10.5).

Состояние сессии хранится в `session.getAttributes()` — это `Map` у каждого сокета: `role`, `deviceId`, `targetAgentId`.

#### `handleAuth`

1. Если первое сообщение не `Auth` → `auth_result{ok:false,"expected auth first"}` и закрыть (`POLICY_VIOLATION`).
2. `DeviceAuthService.authenticate(deviceId, token, role)` → `Result`.
3. Отказ → `auth_result{ok:false, reason}` и закрыть (`NOT_ACCEPTABLE`). В `reason` — только причина, не токен.
4. Успех → записать `role`, `deviceId` в атрибуты.
   - Агент → `sessions.registerAgent`.
   - Телефон → `targetAgentId` → `registerPhone`, вычислить `agentOnline`.
5. Ответ `auth_result{ok:true, reason: newToken, agentOnline}`.

**Хитрость с `reason`:** при самой первой привязке агента по коду релей возвращает **новый постоянный токен в поле `reason`** (единственный раз, когда токен существует в открытом виде). Формат сообщения при этом не менялся. Агент видит `ok=true` + непустой `reason` → сохраняет токен. Это «перегрузка» поля — работает, но на защите стоит назвать как технический долг (лучше отдельное поле `newToken`).

#### `handlePair`

`DeviceAuthService.pairPhone(code)` → `pair_result{ok, deviceId=agentId, deviceToken, deviceName}` или `{ok:false, reason}`. **Соединение сразу закрывается** — это разовый обмен; дальше телефон войдёт обычным `auth`. Токен в лог не пишется.

#### `handleCommand` — главный путь команды

```
1. role != PHONE → игнор (команды шлёт только телефон)
2. command is NaturalLanguage → intentParser.parse(text, requestId)     ← связка разборщиков, раздел 10
       null → audit(ERROR "не понял") + command_result{ERROR,"не понял команду"}; return
3. denied = whitelist.denyReason(command)                                ← имя команды И цель задачи агенту
       denied != null → lessons.reject(requestId)
                        audit(DENIED) + command_result{DENIED,"команда запрещена: <причина>"}; return
4. agent = sessions.agentFor(targetAgentId)
       нет/закрыт → lessons.reject(requestId)
                    audit(ERROR "агент не в сети") + command_result{ERROR,"агент не в сети"}; return
5. audit(SENT)
6. Start/StopScreenStream → sessions.setStreaming
7. отправить агенту command_request(тот же requestId, (возможно переписанная) команда)
```

Порядок **важен**: белый список проверяется **после** ИИ — поэтому даже если ИИ «уговорили» выдать `shutdown`, он не пройдёт.

Что изменилось в этом пути:

- В разборщик теперь передаётся `requestId`: если фразу поймёт только Gemini, «урок» привяжется к этому запросу и будет ждать его результата.
- Вместо `isAllowed` — `denyReason`: человек на телефоне видит **причину** («команда запрещена: агенту нельзя поручать: выключение компьютера»), а не безликое «запрещена».
- `lessons.reject` в ветках отказа: запрещённому свою модель не учим, а команда, которая не выполнялась, урок подтвердить не может.
- `answer_question` и `set_display_option` идут тем же путём, что всё остальное: белый список → аудит → агент. Фразой их не вызвать — их шлёт приложение.

#### `forwardToPhones`

Только от агента: `CommandResult`, `ScreenFrame`, `AgentStep`, `AgentQuestion`, `AgentPlan` → всем `phonesOf(agentId)`. Отдельная ветка в релее нужна только сообщениям, которые агент шлёт **сам, посреди задачи** (шаг, вопрос, план); буфер обмена, файлы и т.п. едут внутри `CommandResult.data`.

Вопрос агента получают **все** телефоны этого ПК, а ответить может любой: агент примет первый ответ с верным `questionId`, остальным вернёт «вопрос уже неактуален».

#### `send`

```java
synchronized (session) { session.sendMessage(new TextMessage(json)); }
```

Сокет нельзя писать из двух потоков одновременно (например, кадр стрима и результат команды) — поэтому блокировка на объекте сессии.

#### Ping

Релей **отвечает** `pong` на `ping`, но сам пинги **не рассылает** (комментарий в Kotlin-протоколе «Relay pings» не соответствует коду). Живость соединения держится TCP и таймаутом простоя.

## 7. Авторизация и привязка

### 7.1 Три вида «пропусков»

| Что | Где хранится | Как выглядит | Живёт |
|---|---|---|---|
| Одноразовый код | `pairing_codes` (открытым текстом) | 6 цифр `482931` | 10 минут, 1 раз |
| Постоянный токен агента | `devices.token_hash` (BCrypt) | 32 случайных байта в base64url | Пока не удалят |
| Постоянный токен телефона для ПК | `phone_bindings.token_hash` (BCrypt) | то же | Пока не удалят |
| Админ-токен | `.env` | строка | Постоянно |

Код бывает двух типов:
- `agent_id = NULL` → **код устройства**: регистрирует новый ПК через `auth`.
- `agent_id = 'pc-…'` → **код телефона**: даёт телефону доступ к этому ПК через `pair_request`.

Код одного типа нельзя использовать для другого (`isForPhone()` проверяется в `tryConsume`).

### 7.2 `DeviceAuthService.authenticate` — три пути

```
authenticate(deviceId, token, role):

  Путь 1 — телефон, привязанный к ПК (новая схема):
    role == PHONE и есть phone_bindings с agent_id == deviceId
      → токен совпадает с ЛЮБЫМ из хэшей? → success(targetAgentId = deviceId)
      → иначе fail("bad token")

  Путь 2 — известное устройство из devices (агент или телефон старой схемы):
    devices.findById(deviceId) есть
      → роль совпадает? токен совпадает с хэшем? → success(null)

  Путь 2б — новое устройство:
    token трактуется как одноразовый код устройства
      → pairingService.tryConsumeDeviceCode(token)
      → нет → fail("unknown device or invalid pairing code")
      → есть → сгенерировать токен, сохранить Device(deviceId, label, role, BCrypt(token))
             → paired(newToken)   ← вернётся в auth_result.reason
```

Обрати внимание: у телефона `deviceId` в `auth` — это **id агента**. Поэтому один телефон, привязанный к трём ПК, имеет три разных токена и входит в три «разных» `deviceId`.

`generateToken()`: `SecureRandom` → 32 байта → Base64 URL-safe без `=`. `SecureRandom` — криптостойкий генератор (обычный `Random` предсказуем).

### 7.3 `DeviceAuthService.pairPhone(code)`

1. Пустой код → отказ.
2. `tryConsumePhoneCode(code)` — существует, не истёк, не использован, **выписан для телефона**.
3. Найти агента `agentId` в `devices`.
4. Сгенерировать токен, сохранить `PhoneBinding(agentId, label, BCrypt(token))`.
5. Вернуть `(agentId, имя ПК, токен)`.

### 7.4 `PairingService`

- `generateCode(label, agentId)` — 6 случайных цифр (`String.format("%06d", …)`), повтор, пока код уникален; срок = сейчас + `ttl-minutes`.
- `tryConsume(code, forPhone)` — найти, проверить `isValidNow` (не `used` и не истёк) и тип; пометить `used=true, usedAt=now`. Второй вызов с тем же кодом вернёт пусто — это и есть «одноразовость».

### 7.5 `AgentAuthService`

Общая проверка для REST-эндпоинтов агента: `deviceId` есть в `devices`, роль `AGENT`, токен совпадает с хэшем. Используется в `AgentPairingController` и `AgentLlmController` (агент присылает `X-Device-Id` и `X-Device-Token`).

### 7.6 BCrypt — почему не просто сравнить строки

BCrypt превращает токен в хэш вида `$2a$10$...` с солью. Из хэша токен **не восстановить**, а проверка специально медленная (~десятки мс) — перебор дорог. Если базу украдут, токены не утекут. `passwordEncoder.matches(presented, hash)` — единственный способ проверить.

Цена: чтобы найти телефон, приходится прогонять `matches` по всем привязкам ПК (их обычно 1–3 — не страшно).

## 8. REST-эндпоинты

| Метод и путь | Класс | Кто вызывает | Защита | Тело → ответ |
|---|---|---|---|---|
| `POST /api/pairing-codes` | `PairingController` | Администратор, `start-jarvis.ps1`, `pair-phone.ps1` | Заголовок `X-Admin-Token` | `{label, agentId?}` → `{code, expiresAt, agentId}`. С `agentId` — код телефона (ПК должен существовать и быть агентом) |
| `POST /api/agent/register` | `AgentRegistrationController` | Новый агент (кнопка «Подключить») | Выключатель `open-registration` + лимит 10/час на IP | `{label}` → `{code, expiresAt}` (код устройства). Выключено → **403** |
| `POST /api/agent/phone-pairing-code` | `AgentPairingController` | Агент (окно «Привязать телефон») | `X-Device-Id` + `X-Device-Token` агента | `{label}` → `{code, expiresAt}` — код телефона **только для себя** |
| `POST /api/agent/llm/generate` | `AgentLlmController` | Vision-агент, планировщик и проверяющий на ПК | `X-Device-Id` + `X-Device-Token`, 20 запросов/мин, тело ≤ 6 МБ | `{prompt, imageBase64?, mimeType?}` → `{text}` |
| `POST /api/admin/llm/generate` | `AdminLlmController` | Скрипты обучения `jarvis-ml` (`build_trainset.py`, `distill.py`) — Gemini как «учитель» | `X-Admin-Token` | `{prompt, temperature?=0.9, json?=true}` → `{text}`; ошибка Gemini → **502** |
| `POST /api/admin/intent/parse` | `IntentEvalController` | Скрипт замера `eval/intent_eval.py` | `X-Admin-Token` | `{phrase, engine?}` → команда, кто разобрал, уверенность, время. `engine`: `stub` / `gemini` / `local` / `system` (по умолчанию) |
| `GET /api/admin/intent/lessons` | `IntentEvalController` | `jarvis-ml/retrain.py` | `X-Admin-Token` | → список подтверждённых уроков `{phrase, command, localAnswer, confirmedAt}` |

Три админских эндпоинта — **служебные, для научной части**: рабочему пути команды они не нужны. Их общий смысл — инвариант 3: скрипты на Python ключа Gemini не знают, они предъявляют админский секрет, а ключ остаётся на релее. `/parse` команды **никуда не отправляет** — ни агенту, ни в журнал аудита: только разбирает и возвращает результат. В режиме `system` он проверяет ещё и белый список с запретом опасных целей: запрещённая команда возвращается как «не понял» с пометкой `denied`. Вызовы `gemini` тратят квоту модели — поэтому секрет.

**Сравнение админ-токена за постоянное время** (`MessageDigest.isEqual`): обычное `equals` выходит на первом несовпавшем символе, и по времени ответа можно угадывать секрет посимвольно. `isEqual` сравнивает всё целиком.

**Почему открытая регистрация не опасна для чужих ПК** (из javadoc `AgentRegistrationController`): она даёт зарегистрировать только **самого себя** как новое устройство. Доступ к чужому ПК требует кода телефона, который показывает сам этот ПК. Риск — только «насоздают пустых устройств», поэтому есть выключатель и лимит по IP (в памяти, сбрасывается при перезапуске — защита от зацикливания клиента, а не от ботнета).

|---|---|---|

| `IntentLesson` | `intent_lesson` | «Уроки» для своей модели: фраза, которую понял только Gemini, и команда, в которую он её превратил |

Поля `intent_lesson`:

| Поле | Смысл |
|---|---|
| `phrase` / `phrase_norm` | Фраза как сказана / приведённая к виду для поиска (по ней повтор той же фразы отвечается из памяти) |

`AuditService.log` использует `deviceRepository.getReferenceById(deviceId)` — «ссылку» без лишнего `SELECT` (устройство точно есть — только что по нему вошли).

## 10. ИИ: разбор фраз и прокси для агента

### 10.1 `IntentParser` — интерфейс

```java
Command parse(String phrase);                       // null = не понял
default Command parse(String phrase, String requestId) { return parse(phrase); }
```

Вторая форма — с `requestId` запроса телефона: она нужна только связке, чтобы привязать «урок» к запросу и потом узнать, выполнилась ли команда.

Три реализации: `HybridIntentParser` (с `@Primary` — его получает обработчик WebSocket), `GeminiIntentParser` и `StubIntentParser`. Сменить провайдера (OpenAI, другая локальная модель) = написать новый `@Component` — обработчик менять не нужно. Именно так 5 октября была добавлена своя модель: появился новый класс с `@Primary`, а логика обработчика сокета осталась прежней.

### 10.1а `HybridIntentParser` — связка, которая на самом деле отвечает телефону

```
фраза
  │ 1. «навык …» / «запусти скрипт …»   ── код (StubIntentParser.skillOrScript), без моделей
  │ 2. уже выученный урок (та же фраза)   ── память (IntentLessons.recall), без моделей
  │ 3. НАША модель (LocalIntentParser → Ollama, ~0,1–0,3 с)
  │       уверена (≥ 0,9) и ответ годный ─────────► команда            источник: local
  │       не уверена / «не понял» / мусор / недоступна
  ▼
  4. Gemini (интернет, 2–3 с) ── понял ──────────► команда + УРОК     источник: gemini
  │       недоступен → минуту его не трогаем
  ▼
  5. годный ответ нашей модели                                          источник: local-offline
     иначе регулярные выражения (StubIntentParser)                      источник: stub / none
```

Метод `decide(phrase, requestId)` возвращает `Decision(command, source, confidence, localRaw, localMs, geminiMs)` — не только команду, но и **кто** её разобрал, с какой уверенностью и за сколько. Это идёт в лог (`Разбор «сделай потише» -> set_volume [local, уверенность 0.99]`) и в замеры.

Детали, которые стоит уметь объяснить:

- **Режимы** (`jarvis.intent.engine`): `auto` — вся цепочка; `local` — без Gemini (офлайн); `gemini` — без своей модели, как было раньше. Пока модели в Ollama нет, `auto` ведёт себя как `gemini` — релей с этим кодом можно ставить заранее.
- **Три причины уйти в Gemini:** ответ не прошёл проверку формата; модель сказала «не понял»; уверенность ниже порога. Уверенность — произведение вероятностей слов ответа, которые отдаёт Ollama.
- **«Не понял» перепроверяется всегда** (`trust-unknown-above = 2.0`, а уверенность не бывает больше 1): вдруг Gemini поймёт необычную формулировку. Цена — платный запрос на каждую болтовню.
- **Предохранитель** `geminiDownUntil`: если Gemini только что не ответил (нет интернета, кончилась квота), минуту его не спрашиваем. Иначе каждая непонятная фраза ждала бы заведомо неудачного запроса — замер 6 октября показал около полсекунды на фразу.
- **Урок записывается, только если своя модель была спрошена и не справилась.** Если её просто нет — это не «чего она не знает», а «её не спросили».
- **Белый список и запрет опасных целей — после разбора**, в обработчике сокета, одинаково для любого из пяти путей.

`LocalIntentParser` — HTTP-клиент к Ollama: шлёт фразу, получает JSON и вероятности, **проверяет ответ кодом** (тип из списка, громкость 0–100, адрес с точкой и т.п.) и возвращает `Result(kind, command, confidence, raw, ms)`, где `kind` — `COMMAND`, `UNKNOWN` или `UNAVAILABLE`. Таймаут 20 с — с запасом на первую загрузку модели в память. Формат ответа модели, обучение и цифры — файл 5.

### 10.2 `GeminiIntentParser`

Теперь это **вторая ступень** связки и «учитель». У него два входа: `parse(phrase)` — с короткими путями и запасным разбором правилами (так он работает в режиме `gemini`), и `parseModelOnly(phrase)` — только модель: `null`, если она ответила «unknown», исключение при любой ошибке. Вторым пользуются связка (ей надо отличать «не понял» от «недоступен») и замеры — обычный `parse` прятал бы ошибки модели за запасным путём.

Как устроен `parse`:

0. Фраза про навык или скрипт → сразу `agent_task`, без модели.
1. Нет ключа → сразу `StubIntentParser` (без сети).
2. Запрос `POST https://generativelanguage.googleapis.com/v1beta/models/<model>:generateContent`, ключ — в заголовке `x-goog-api-key` (не в URL, чтобы не попасть в логи прокси). Таймаут 8 с.
3. Тело:
   - `systemInstruction` — **системный промпт**: список команд с точным JSON-форматом и примерами («сделай потише» → `{"type":"set_volume","level":30}`, «найди на ютубе…» → `agent_task`, «сколько будет 2+2» → `{"type":"unknown"}`);
   - `contents` — фраза пользователя;
   - `generationConfig`: `temperature: 0` (детерминированно), `responseMimeType: application/json` (только JSON).
4. Ответ: `candidates[0].content.parts[0].text` → срезать ```` ```json ```` если модель всё же обернула → если `type == "unknown"` — fallback → иначе `mapper.readValue(json, Command.class)`.
5. **Любая ошибка** (сеть, не 200, кривой JSON, неизвестный `type`) → fallback на regex. Сервис деградирует, но не ломается.

Ключевая идея: модель отвечает **прямо в формате нашего протокола**, и Jackson превращает ответ в `Command` той же магией `@JsonSubTypes`. Если модель выдумала несуществующий тип — Jackson упадёт, сработает fallback. Если выдумала существующий, но опасный (`shutdown`) — его остановит белый список.

Логи: пишется только `имя команды`, **тело ответа Google и ключ не логируются**.

В системном промпте нет команд живого экрана, буфера, файлов, отмены, ответа на вопрос и настроек показа — они отправляются кнопками приложения напрямую, не фразами.

5 октября промпт дополнен двумя правилами, найденными замером: **папки открывает `open_app`**, а не агент, и **запрещённое и неподдерживаемое — «unknown»** (раньше «выключи компьютер» Gemini превращал в задачу агенту — см. раздел 11). Этот же текст промпта берёт `jarvis-ml/distill.py`, когда Gemini размечает живые фразы для обучения своей модели, — учитель и рабочий разборщик отвечают одинаково.

### 10.3 `StubIntentParser` — правила по ключевым словам

| Если во фразе… | Команда |
|---|---|
| начинается с «навык », «выполни навык », «запусти навык », «скрипт », «выполни скрипт », «запусти скрипт » | `AgentTask(фраза целиком, SCREEN, 20)` |
| «потише» / «тише» | `SetVolume(30)` |
| «погромче» / «громче» | `SetVolume(80)` |
| «заблокир» | `LockScreen` |
| начинается с «закрой » | `KillProcess(остаток)` |
| начинается с «запусти » | `OpenApp(остаток)` |
| «процесс» | `ListProcesses` |
| «скрин» / «экран» | `Screenshot` |
| «лайк» / «найди» | `AgentTask(фраза, BROWSER, 15)` |
| «ютуб» / «youtube» | `OpenUrl("https://youtube.com")` |
| «открой X.Y» | `OpenUrl("https://X.Y")` |
| иначе | `null` → «не понял команду» |

Порядок проверок важен: «найди на ютубе» сработает как `agent_task` раньше, чем «ютуб».

Первая строка таблицы — статический метод `skillOrScript`, им пользуются все три разборщика. Почему навыки и скрипты узнаёт **код**, а не модель: «запусти скрипт сервер» легко спутать с «запусти блокнот» (`open_app`), а «навык утро» — вообще не команда, которую модель знает. Что за навык или скрипт — решает уже агент на ПК: только у него есть список выученного. Релей лишь гарантирует, что такая фраза дойдёт до агента быстро и всегда одинаково.

На экзамене из 250 фраз одни эти правила дают 39,6% — это честная цена работы совсем без моделей.

### 10.4 `AgentLlmController` — прокси к Gemini для агента

Зачем: vision-агенту на ПК нужен ИИ, но **ключ не должен лежать на ПК** (инвариант 3). Агент шлёт промпт (и, возможно, скриншот) сюда, релей добавляет ключ и идёт в Google.

Через этот же прокси теперь ходят ещё два «мозга» агента: **планировщик** многоэтапных задач и **проверяющий** результат подзадачи (файл 4). Оба шлют текст без картинки. Лимит 20 запросов в минуту общий на всё устройство — длинная задача по плану тратит его заметно быстрее одиночной.

Проверки по порядку:
1. `X-Device-Id` + `X-Device-Token` → `AgentAuthService` → иначе **401**.
2. Ключ не задан → **503** «LLM is not configured».
3. Тело > 6 МБ → **413**.
4. Больше 20 запросов за минуту с этого устройства → **429** (окно в памяти, `RateWindow` на `deviceId`).
5. Тело — `byte[]`, разбирается вручную, чтобы при ошибке кодировки (не UTF-8 кириллица) ответить понятным **400**, не логируя сам текст.
6. Пустой промпт → **400**.

Запрос к Gemini: `contents.parts = [text, inlineData{mimeType, data}]`, `temperature 0`, таймаут **90 с** (мультимодальный запрос со скриншотом занимает 12–30+ с). **Повтор** при 503 («model is overloaded») и сетевых сбоях: паузы 1 с и 2 с. 429 не повторяется (квота — повтор не поможет).

Ошибка → **502** «gemini call failed». В `finally` — строка в `agent_llm_log` (задержка, успех) и строка в логе (без содержимого).

### 10.5 `IntentLessons` — «не понял → спросил Gemini → запомнил»

```
наша модель не справилась ──► Gemini назвал команду ──► propose()   урок «предложен»
агент выполнил её успешно ───────────────────────────► confirm()   урок «подтверждён»
та же фраза ещё раз ──────────────────────────────────► recall()    ответ сразу, без моделей
накопились подтверждённые ──► jarvis-ml/retrain.py ──► новая версия модели понимает и похожие фразы
```

| Метод | Кто вызывает | Что делает |
|---|---|---|
| `propose(requestId, phrase, command, localAnswer)` | `HybridIntentParser`, когда понял только Gemini | Сохраняет урок без даты подтверждения |
| `confirm(requestId)` | Обработчик сокета на `CommandResult` со статусом `OK` | Ставит `confirmed_at` |
| `reject(requestId)` | Обработчик сокета: результат не `OK`, команда запрещена, агент не в сети | Удаляет неподтверждённые уроки этого запроса |
| `recall(phrase)` | `HybridIntentParser`, ступень 2 | Возвращает команду подтверждённого урока с такой же фразой |
| `confirmed()` | `GET /api/admin/intent/lessons` | Список для дообучения |

Почему урок подтверждается **выполнением**: Gemini тоже ошибается. Если команда не выполнилась или человек её отменил, учить на ней свою модель нельзя — она выучила бы ошибку учителя. Успешное выполнение — самый дешёвый признак «понято верно», для которого не надо ничего спрашивать у человека.

Тонкости:

- У урока-задачи агенту при повторе **цель берётся из того, что человек сказал сейчас**: сохранённая цель заменяется текущей фразой, из записи используются только режим (`browser`/`screen`) и лимит шагов.
- **Чему не учимся никогда:** фразам длиннее 300 символов и фразам со словами про пароль, ПИН, CVV, паспорт, ИИН, номер карты — таких данных в базе быть не должно.
- Любая ошибка базы в этих методах только пишется в лог: недоступная таблица уроков — не повод не выполнить команду.
- Написано и покрыто тестами (`HybridIntentParserTest`), но вживую цикл «урок → дообучение → новая версия» на 13 октября не прогонялся.

### 10.6 `GeminiClient` и `AdminLlmController` — Gemini как «учитель»

`GeminiClient` — простой текстовый запрос к Gemini: без картинок, без формата команд, с настраиваемой температурой (0 — один и тот же ответ, около 1 — разнообразие) и таймаутом 120 с. Нужен там, где Gemini **придумывает** данные для обучения: перефразировки одной просьбы и живые фразы «как говорят люди».

Разбор фраз (`GeminiIntentParser`) и прокси агента (`AgentLlmController`) ходят в Gemini своим кодом — их намеренно не переводили на общий клиент, чтобы не сломать работающее. Это дублирование стоит назвать на защите техническим долгом.

## 11. Белый список и аудит

### `CommandWhitelist.java` — граница безопасности

```java
private static final Set<String> ALLOWED = Set.of(
    "set_volume", "lock_screen", "list_processes", "kill_process",
    "open_url", "open_app", "screenshot", "agent_task",
    "click", "type_text", "scroll",
    "start_screen_stream", "stop_screen_stream",
    "get_clipboard", "set_clipboard",
    "list_files", "send_file_to_phone", "send_file_to_pc",
    "cancel_task",
    "answer_question",        // ответ на вопрос ИИ-агента
    "set_display_option");    // что показывать на экране ПК (рентген, панель плана)
```

`shutdown` и `reboot` **намеренно исключены** — их протокол знает, но до агента они не дойдут (телефон получит `denied`). `nl` тоже не в списке — но он и не должен сюда доходить: к моменту проверки фраза уже заменена конкретной командой.

Почему две новые команды безопасно разрешить:

- `answer_question` сама по себе ничего на ПК не делает: агент примет её, только если **прямо сейчас** ждёт ответа на вопрос с таким же случайным `questionId`, — иначе вернёт «вопрос неактуален».
- `set_display_option` принимает только два ключа (`xray`, `plan`) — настройки безопасности агента через неё не поменять.

Это единственное место, где решается «можно ли». Он стоит **после** ИИ → защищает от prompt injection: ИИ может предложить что угодно, но выполнится только разрешённое.

Kotlin-копия в `jarvis/shared/Whitelist.kt` устарела и нигде не применяется — эталон здесь.

### `denyReason` и `ForbiddenGoals` — вторая проверка

```java
public String denyReason(Command command) {
    if (!ALLOWED.contains(command.name())) return "команды нет в белом списке";
    if (goalsGuard && command instanceof Command.AgentTask task) {
        String why = ForbiddenGoals.reason(task.goal());
        if (why != null) return "агенту нельзя поручать: " + why;
    }
    return null;   // можно
}
```

**Откуда взялась вторая проверка — находка замера 5 октября.** Белый список не пропускает команду `shutdown`. Но фразу «выключи компьютер» Gemini превращал не в `shutdown`, а в **задачу агенту** с целью «выключи компьютер». `agent_task` — команда разрешённая, и агент на ПК дошёл бы мышью до «Пуск → Завершение работы». То же с «отформатируй диск c», «переведи маме пять тысяч», «купи билет»: из 7 таких просьб в экзамене Gemini отправил агенту 6. Имя команды было в порядке — опасной была **цель**.

`ForbiddenGoals.reason(goal)` — список регулярных выражений по тексту цели:

| Причина отказа | Что ловится (примеры) |
|---|---|
| выключение компьютера | «выключи / выруби / отключи / заверши работу» + «компьютер / комп / пк / ноутбук / windows» рядом |
| перезагрузка компьютера | «перезагрузи / перезапусти / ребутни / reboot / restart» + то же |
| форматирование диска | «отформатируй / format» + «диск / флешку / раздел» |
| массовое удаление | «удали / сотри / очисти / снеси» + «все / весь» + «файлы / данные / папки / фото» |
| перевод денег | «переведи / перечисли / скинь / закинь» + деньги, сумма, «на карту» |
| покупка или оплата | «купи / закажи / оплати / оформи заказ» |

Правила **намеренно узкие**: между глаголом и объектом допускается не больше двух-трёх слов, поэтому «выключи звук», «перезагрузи страницу», «переведи текст», «удали файл отчёт» разрешены. `ForbiddenGoalsTest` проверяет оба списка — «должно быть запрещено» и «должно быть разрешено», и второй не короче первого.

Проверка стоит в белом списке, поэтому действует **одинаково** для любого разборщика, для рецептов с телефона (они приходят готовой `agent_task`, минуя разбор) и для уроков из памяти. Выключатель — `JARVIS_FORBIDDEN_GOALS=false`, на случай ложного запрета на защите.

Честная оговорка: это список правил, а не понимание. Необычную формулировку он может пропустить — тогда остаются защиты агента (запрет терминала, подтверждения на ПК и на телефоне, отказ вводить пароли).

### `AuditService` — журнал

Одна строка на каждую команду: `SENT` (ушла агенту), `DENIED` (белый список), `ERROR` (не понял / агент офлайн). Результат выполнения (успех на ПК) **не пишется** — только факт отправки.

Нюанс: для телефона новой схемы `deviceId` в сессии = id **агента**. Поэтому в `audit_log` команда телефона записывается на устройство-ПК, и различить, **какой именно** из нескольких телефонов её дал, нельзя. Улучшение: хранить id привязки (`phone_bindings.id`) в атрибутах сессии и писать его.

### `C:\diplom\faust.ps1` — основной запуск (через `start-faust.bat`)

Лежит не в папке релея, а в корне проекта, потому что поднимает **всё**: Docker, релей, свою модель, агента. Что он делает для релея (`Start-Relay`):

## 15. Модель безопасности и честные слабые места

**Что сделано хорошо:**
- Токены только в виде BCrypt, одноразовые коды с TTL, `SecureRandom`.
- Белый список **после** ИИ; `shutdown/reboot` вне списка.
- Запрет опасных **целей** у задачи агенту (`ForbiddenGoals`) — закрыта дыра, найденная замером: «выключи компьютер» как `agent_task`.
- Ответ своей модели проверяется кодом (формат, диапазоны), а при неуверенности — перепроверяется Gemini; ни одной модели на слово не верим.
- В «уроки» не попадают фразы с паролями и платёжными данными; урок засчитывается только после успешного выполнения.
- Служебные эндпоинты обучения и замеров закрыты админским секретом; `/parse` команды никуда не отправляет.
- Ключ ИИ только в `.env`, не логируется ни ключ, ни тело ответа Google, ни токены.
- Админ-токен сравнивается за постоянное время.
- Лимиты: 20 запросов ИИ/мин на агента, 10 регистраций/час на IP, 6 МБ тело, 8 МБ сообщение.
- Контейнер работает не от root, в образе нет компилятора.

**Что стоит назвать самому на защите:**
1. **Нет TLS** — `ws://` и `http://`. Токены и скриншоты идут открытым текстом. Решение: обратный прокси с HTTPS (Caddy/nginx + Let's Encrypt) → `wss://`; или Tailscale (шифрует туннель).
2. `setAllowedOrigins("*")` — для не-браузерных клиентов безопасно, но стоит сузить.
3. Дефолтный `dev-admin-change-me` — опасен, если релей виден из интернета.
4. Аудит не различает телефоны одного ПК (см. раздел 11) и не пишет итог выполнения.
5. `protocolVersion` не проверяется.
6. Нет серверных пингов; мёртвое соединение обнаруживается по таймауту TCP/простоя.
7. `SessionRegistry` и лимиты — в памяти: один экземпляр релея, без горизонтального масштабирования.
8. `ddl-auto: update` вместо миграций.
9. Перегрузка поля `reason` для передачи токена.
10. Токены бессрочные; нет ротации и API отзыва (кроме удаления строки в БД).
11. **Фразы пользователя теперь хранятся в базе** (`intent_lesson.phrase`) — те, что понял только Gemini. В лог релея фраза писалась и раньше (сейчас — `Разбор «…»`, первые 80 символов). Хранение в базе — осознанная плата за самообучение; в продукте нужны срок хранения и согласие.
12. Запрет опасных целей — список регулярных выражений, а не понимание: необычную формулировку он пропустит, а «закажи пиццу» и «купи билет» запретит всегда — даже если человек именно этого и хотел. Покупки и оплата закрыты целиком сознательно.
13. За точность связки платит Gemini: каждое «не понял» и каждый ответ с уверенностью ниже 0,9 — платный запрос (на экзамене А это 16% фраз).
14. Три обращения к Gemini написаны тремя разными кусками кода (`GeminiIntentParser`, `AgentLlmController`, `GeminiClient`).
15. Адрес Ollama зашит как `host.docker.internal` — релей на отдельном сервере без своей Ollama тихо работает в режиме `gemini`.
16. Самообучение на уроках написано и покрыто тестами, но вживую не прогонялось.

**Модель угроз коротко:** злоумышленник без токена → не войдёт; с украденным телефоном → сможет только разрешённые команды, опасные потребуют подтверждения человека за ПК (агент), всё в аудите; prompt injection → ИИ может «захотеть» опасного, но белый список, запрет опасных целей и проверки агента это отсекут; утечка БД → хэши токенов и накопленные фразы-уроки, ключа ИИ там нет; подмена своей модели в Ollama → её ответ всё равно проходит проверку формата, белый список и запрет целей.

## 17. Как расширять

**Новая команда:** `record` + `@JsonSubTypes` в `protocol/Command.java` (и то же в агенте и Kotlin) → имя в `CommandWhitelist` → при необходимости строка в системном промпте `GeminiIntentParser` и правило в `StubIntentParser` → пересобрать релей.

Если команду должны вызывать **фразой**, теперь есть ещё три места: тип и проверка параметров в `LocalIntentParser.interpret` (иначе ответ своей модели с новым типом не пройдёт проверку формата), шаблоны в `jarvis-ml/build_trainset.py` + переобучение (иначе своя модель о команде не узнает и фраза будет уходить в Gemini), фразы в экзамен `eval/build_testset.py`. Пока модель не переобучена, система всё равно работает — через Gemini.

**Новое сообщение от агента телефону** (как `agent_question`): `record` + `@JsonSubTypes` в `JarvisMessage.java` трёх копий → ветка `case … -> forwardToPhones` в `handleTextMessage`. И обновлять релей вместе с агентом.

**Другой LLM для разбора фраз:** новый класс `implements IntentParser` — либо как ещё одна ступень внутри `HybridIntentParser`, либо с `@Primary` вместо него. Другая **локальная** модель — просто другое имя в `JARVIS_LOCAL_LLM_MODEL` (формат ответа должен совпасть). Для агента — поменять `askGemini` в `AgentLlmController`.

**Новое правило запрета:** строка `rule("причина", "регулярка")` в `ForbiddenGoals` + по примеру в оба списка `ForbiddenGoalsTest` («запрещено» и «разрешено»).

**Команда требует подтверждения на сервере:** можно не отправлять агенту сразу, а слать телефону запрос подтверждения — но сейчас подтверждение живёт на ПК (`ConfirmationGate`), и это сознательно: человек за компьютером видит, что происходит.

**Миграции:** добавить Flyway, скрипт `V1__init.sql` из текущей схемы, `ddl-auto: validate`.
