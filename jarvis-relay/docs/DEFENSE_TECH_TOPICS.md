# Jarvis: технологии и темы для защиты

Шпаргалка по всем ключевым темам проекта — сгруппированы по слоям
архитектуры, с кратким «что это» и «зачем именно здесь», чтобы можно было
не просто назвать технологию, а объяснить её роль.

## 1. Протокол и связь между тремя частями системы

- **WebSocket** — постоянное двустороннее соединение (не HTTP-запрос-ответ)
  между телефоном/агентом и релеем. Нужен именно он, а не обычный REST,
  потому что релей должен сам, без опроса, мгновенно прислать команду ПК
  или результат телефону.
- **Kotlin Multiplatform (KMP), модуль `shared`** — общий Kotlin-код,
  который компилируется и в Android-приложение, и (как JVM-библиотека) в
  Java-релей и Java-агента. В нём описан весь протокол (`Command`,
  `JarvisMessage`) один раз, а не три раза в трёх кодовых базах — так три
  стороны физически не могут разъехаться в формате сообщений.
- **kotlinx.serialization + sealed-иерархии** — `Command` и `JarvisMessage`
  это `sealed interface`: закрытый, перечислимый набор типов. Каждый
  вариант сериализуется в JSON с полем-дискриминатором `"type"`. Закрытость
  набора — часть модели безопасности: whitelist ниже проверяет именно
  список типов из этого sealed-интерфейса.
- **requestId (UUID)** — каждый запрос и его ответ связаны одним id, чтобы
  при параллельных командах не перепутать, какой `CommandResult` к какому
  `CommandRequest` относится.

## 2. Релей (бэкенд)

- **Spring Boot (Java 21)** — сервер, через который проходит вообще всё:
  и WebSocket-канал, и REST-эндпоинты для паринга.
- **Spring WebSocket (`TextWebSocketHandler`)** — один Java-класс
  (`JarvisWebSocketHandler`) обрабатывает КАЖДОЕ соединение: авторизация
  первым сообщением, маршрутизация «команда от телефона -> нужному агенту»,
  «результат от агента -> телефонам, которые им управляют».
- **PostgreSQL + JPA/Hibernate** — хранит устройства (`devices`), привязки
  телефонов к ПК (`phone_bindings`), одноразовые коды паринга
  (`pairing_codes`) и журнал аудита команд.
- **Docker / docker-compose** — релей и база разворачиваются как два
  контейнера одной командой, без ручной установки Java/Postgres на сервер.
- **REST API рядом с WebSocket** — паринг-коды и самообслуживание агента
  (получить код для своего телефона) сделаны обычными HTTP-эндпоинтами, а
  не через WebSocket — это разовые запрос-ответ операции, WebSocket для
  них избыточен.

## 3. Модель безопасности (ядро дипломной работы)

- **Whitelist команд (`CommandWhitelist`)** — что бы ни предложила LLM в
  ответ на голосовую фразу, на ПК уйдёт только команда из явного списка
  разрешённых типов. Это главный аргумент против prompt injection: даже
  если сформулировать голосовую команду так, чтобы обмануть модель,
  результат всё равно проверяется по statically известному списку, а не
  по тому, что «попросила» модель.
- **Двухуровневое доверие**: админский секрет (`X-Admin-Token`) нужен
  только для регистрации НОВОГО ПК; привязка телефона к уже
  зарегистрированному ПК — самообслуживание по одноразовому короткому
  коду, без секретов вообще.
- **BCrypt** — постоянные токены устройств хранятся в базе только как
  хэш, не в открытом виде.
- **Одноразовые коды паринга** — короткоживущие (TTL), гасятся при первом
  использовании (в таблице отмечается использованный), что делает их
  бесполезными для повторного применения даже при перехвате.
- **Constant-time сравнение (`MessageDigest.isEqual`)** для админского
  токена — защита от тайминг-атаки (угадывание секрета по времени ответа).
- **Fail-closed подтверждение на ПК** — перед чувствительными командами
  (kill_process, agent_task, передача файлов) на самом ПК всплывает
  диалог с таймером; если человек не успел ответить — команда
  автоматически ОТКЛОНЯЕТСЯ, а не выполняется.
- **Принцип наименьших привилегий** — агент выполняется под обычной
  учётной записью залогиненного пользователя, без повышения прав; это
  честный ответ на вопрос «а что если кто-то взломает релей» — ущерб
  ограничен тем, что и так может сделать сам пользователь ПК.

## 4. Агент на ПК

- **Java 21, десктопное приложение** (не веб, не сервис) — работает как
  обычная программа с иконкой в трее.
- **java.awt.Robot** — низкоуровневое управление мышью/клавиатурой и
  захват экрана на уровне ОС; это то, что физически превращает команду
  «кликни туда-то» в реальное действие на экране.
- **Selenium** — для агента компьютерного зрения в браузере: вместо клика
  по пикселям он работает через DOM-модель страницы, это надёжнее для
  веб-задач, чем чистый pixel-based клик.
- **java.net.http.WebSocket** — встроенный в JDK клиент, без сторонних
  библиотек, для постоянного соединения с релеем.
- **Swing** — все окна агента (иконка в трее, окно привязки телефона,
  окно подтверждения команды, мастер первого запуска).
- **jpackage** — упаковка Java-приложения в нативный `.exe`/`.msi` со
  встроенным JRE, чтобы конечному пользователю не нужно было отдельно
  ставить Java.
- **Многопоточность через `ExecutorService`** — долгие операции (задача
  vision-агента, ожидание диалога подтверждения) уводятся в отдельные
  потоки, чтобы не блокировать чтение WebSocket-сокета — иначе, например,
  команда отмены не дошла бы до конца долгой задачи.

## 5. ИИ-ядро: LLM и компьютерное зрение

- **Google Gemini** — используется в двух ролях: (1) превращает
  произвольную голосовую фразу в одну из конкретных команд протокола
  (intent parsing), (2) выступает «мозгом» агента компьютерного зрения.
- **Трёхуровневая модель команд**: сырая natural-language фраза → (только
  на релее) LLM превращает её в конкретную типизированную команду →
  whitelist проверяет → агент либо выполняет системную команду напрямую,
  либо запускает цикл vision-агента с низкоуровневыми действиями
  (клик/ввод текста/скролл).
- **Цикл computer-use агента**: снимок экрана/DOM → модель предлагает
  следующее действие → выполнение → новый снимок → повтор, с ограничением
  числа шагов и поддержкой отмены на любом шаге.
- **LLM-прокси на релее** — ключ API живёт только в переменных окружения
  сервера и никогда не попадает ни в APK, ни в агента, ни в логи. Это
  осознанное архитектурное решение по безопасности, а не просто «так
  получилось».

## 6. Мобильное приложение

- **Jetpack Compose** — весь UI написан декларативно на Kotlin.
- **ViewModel + StateFlow/Flow (MVVM)** — состояние экрана (статус связи,
  список устройств, история задач) живёт во ViewModel и стримится в UI.
- **OkHttp** — WebSocket-клиент на стороне приложения, с собственной
  логикой переподключения (экспоненциальная задержка).
- **DataStore** — постоянное локальное хранилище: список привязанных ПК,
  какой из них активный, настройки.
- **Vosk** — полностью офлайн-распознавание речи; используется и для
  ключевого слова «Джарвис» (wake-word), и для самих голосовых команд —
  выбран вместо облачных решений именно из-за офлайн-работы и отсутствия
  регистрации/лимитов.
- **Foreground Service** — держит соединение и (при включённом wake-word)
  микрофон живыми, даже когда приложение свёрнуто, с уведомлением о
  статусе задачи.
- **Корутины Kotlin** — асинхронные сетевые вызовы, в т.ч. специальный
  паттерн «одноразового» WebSocket-соединения (открылись, дождались
  одного ответа, закрылись) для лёгких операций вроде проверки
  онлайн-статуса ПК.

## 7. Сетевая связность

- **Агент всегда подключается САМ, наружу, к релею** — а не наоборот. Это
  и есть решение проблемы NAT: домашнему ПК не нужен проброс портов,
  чтобы получать команды, потому что именно он инициирует соединение.
- **Wake-on-LAN** — телефон может «разбудить» выключенный ПК
  UDP-«магическим пакетом»; в пределах одной сети — широковещательно, вне
  сети — точечно на последний известный публичный IP, который релей сам
  запоминает при каждой успешной авторизации агента.
- **Caddy как reverse proxy** — перед релеем в проде стоит Caddy, который
  сам получает и продлевает TLS-сертификат (Let's Encrypt), так что
  соединение с релеем идёт по `wss://`, а не по голому `ws://`.
- **Автопереподключение с экспоненциальной задержкой** — и на телефоне, и
  на ПК: обрыв связи не требует ручного перезапуска.

## 8. Развёртывание / инфраструктура

- **Docker Compose** — relay + PostgreSQL (+ Caddy в проде) поднимаются
  одной командой на любой машине.
- **VPS-хостинг (выбран Hetzner)** — сравнивались бесплатные варианты
  (Oracle/Google Cloud free-tier, разные PaaS), но для постоянного
  WebSocket-сервера они не подходят (спящие простаивающие контейнеры,
  ограничения по времени жизни соединения) — отсюда выбор недорогого, но
  честного постоянно работающего VPS.
- **Конфигурация через переменные окружения** — все секреты (админ-токен,
  ключ LLM, пароль базы) задаются переменными окружения, а не хранятся в
  коде — стандартная практика («12-factor app»).

## 9. Измеримая часть (научная составляющая диплома)

- **Журнал аудита в PostgreSQL** — фиксирует каждую команду (кто, что,
  разрешено/отклонено), это и есть сырые данные для метрик.
- **План замера**: точность распознавания намерения (сколько голосовых
  фраз LLM правильно превратила в команду) и процент успешно выполненных
  задач на фиксированном наборе фраз — то, что превращает проект из
  просто «сделал приложение» в «сделал и измерил», что требуется по теме
  диплома.
- **Живая демонстрация whitelist** — можно на защите показать вживую, как
  специально сформулированная «вредная» фраза доходит до LLM, но
  блокируется на whitelist до того, как попасть на ПК — наглядный и
  честный аргумент про безопасность.

---

### Если спросят одним предложением про каждый слой

- **Протокол**: один общий Kotlin-модуль с закрытым набором типов
  сообщений, JSON с дискриминатором типа.
- **Релей**: Spring Boot + WebSocket + PostgreSQL, посредник и
  единственная точка входа в систему.
- **Безопасность**: whitelist команд + одноразовые коды + BCrypt +
  fail-closed подтверждение на ПК.
- **Агент**: Java + java.awt.Robot/Selenium, дозванивается сам, наружу.
- **ИИ**: Gemini для перевода речи в команду и для управления экраном,
  ключ только на сервере.
- **Приложение**: Jetpack Compose + OkHttp + Vosk (офлайн-голос).
- **Инфраструктура**: Docker Compose на VPS за Caddy (TLS).
