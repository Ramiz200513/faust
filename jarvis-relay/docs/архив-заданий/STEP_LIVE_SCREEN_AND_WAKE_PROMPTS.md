# Jarvis — следующий шаг: живой экран (стриминг) + пробуждение ПК с телефона

Научная часть (`STEP_EVAL_AND_FEATURES_PROMPTS.md`) написана, но пока **отложена** — сначала
ещё функции. Как пользоваться: каждому ИИ-агенту — «Общий контекст» + промпт своего
подпроекта. Порядок: **Релей → Агент → Приложение**. После каждого пункта — как проверить.

---

## Общий контекст (вставлять в начало КАЖДОГО промпта)

```
Проект Jarvis — управление ПК с телефона естественным языком (дипломная, тема
«AI-агент для автоматизации многоэтапных пользовательских задач»).
Автор учится: объясняй код по ходу, по-русски, маленькими проверяемыми шагами,
после каждого шага — как проверить.

Архитектура (Windows 11):
  Телефон (KMP/Compose) <--WS--> Релей (Spring Boot, Java 21, Docker) <--WS--> Агент (Java 21, трей)
  C:\diplom\jarvis          — :shared (протокол Kotlin) + :androidApp (Compose)
  C:\diplom\jarvis-relay    — релей + PostgreSQL, docker compose (restart: unless-stopped)
  C:\diplom\jarvis-agent    — агент: AgentTray, PairPhoneDialog (окно с QR), CommandExecutor,
                              LanAddress (подбор адреса для QR), RelayClient (WebSocket-клиент)

ИНВАРИАНТЫ (не ломать):
 1. Протокол WebSocket (JarvisMessage/Command, пакет protocol/) меняется синхронно в 3 местах:
    Kotlin :shared, Java релей, Java агент; JSON 1:1, дискриминатор "type".
 2. CommandWhitelist (релей) — граница безопасности; новая команда добавляется туда явно.
    shutdown/reboot вне списка.
 3. Ключ LLM только в .env релея, не в агенте/APK. Не относится к этому шагу напрямую.
 4. Агент сам звонит на релей. Токены/deviceId переживают перезапуск, не логировать их.

ТЕКУЩЕЕ СОСТОЯНИЕ (важно — проверено чтением кода):
- Всё работает: привязка по QR (агент в трее → «Привязать телефон» → PairPhoneDialog строит
  QR вида jarvis-pair://pair?code=..&relay=..&name=.., телефон сканирует через
  PairingQr.parse), релей+Postgres в Docker, разбор фраз через Gemini с откатом на regex,
  open_app/set_volume настоящие, agent_task (vision) работает через прокси релея.
- Пробуждение ПК ИЗ СНА уже проверено вручную (не в коде): на этом ноутбуке Wake-on-LAN
  работает ТОЛЬКО по кабелю Ethernet (Realtek), Wi-Fi адаптер (MediaTek) magic packet не
  принимает. У ПК должна быть включена галочка «Wake on Magic Packet» в свойствах адаптера
  и подключён кабель — это пользователь настраивает в Windows сам, в коде это не проверяется.
- ScreenFrame в протоколе УЖЕ имеет поле seq (Int?) с комментарием «индекс кадра при
  стриминге; null — для одиночного скриншота» — то есть протокол изначально был рассчитан на
  стрим, просто он не реализован. Используй именно seq как признак «это кадр стрима», не
  добавляй отдельное поле.
- Научная часть (docs\STEP_EVAL_AND_FEATURES_PROMPTS.md — журнал точности LLM, open_file,
  экран «История») написана, но ОТЛОЖЕНА — не запускай её сейчас, если явно не попросят.
```

```
Задача: минимальные изменения — добавить две новые команды в whitelist. Сама пересылка

R2. CommandWhitelist.ALLOWED — добавь "start_screen_stream", "stop_screen_stream".

R3. (Необязательно, но полезно для диплома) в SessionRegistry можно отметить, что у агента
  идёт стрим — например boolean-флаг рядом с сессией агента — тогда DevicesScreen сможет
  когда-нибудь показать «идёт стрим». Делай только если легко ложится на текущий код, это не
```

## Промпт 2 — АГЕНТ (`C:\diplom\jarvis-agent`)

```
[Общий контекст]

Задача: живой экран (периодические кадры вместо одного скриншота) + пробуждение ПК —
здесь это значит отдать телефону MAC-адрес ПК через QR, сама отправка magic-пакета будет
в приложении (следующий промпт). Протокол уже согласован с релеем (см. его промпт R1):
Command.StartScreenStream(fps, maxWidth) / Command.StopScreenStream().

## Часть А — живой экран

A1. protocol/Command.java (Java-зеркало агента, ДОЛЖНО совпадать 1:1 с релеем — те же поля и
  "type"): добавь те же две record, что и на релее (R1 из его промпта).

A2. Главная сложность: CommandExecutor.execute(...) сейчас ВОЗВРАЩАЕТ список сообщений на
  ОДНУ команду — этого достаточно для скриншота (один кадр), но для стрима нужно слать кадры
  МНОГО РАЗ САМОСТОЯТЕЛЬНО, не дожидаясь новой команды. Значит, CommandExecutor (или новый
  класс ScreenStreamer, если удобнее вынести) должен уметь ОТПРАВЛЯТЬ сообщения сам, а не
  только возвращать их. Посмотри, как RelayClient сейчас шлёт сообщения (приватный метод
  send(...) у него уже есть — он вызывается и для Pong, и для результатов execute()) и
  прокинь в CommandExecutor callback вида Consumer<JarvisMessage> (тот же send, что уже
  использует RelayClient) — через конструктор, как уже прокинуты другие зависимости.

A3. ScreenStreamer (новый класс в пакете agent, рядом с CommandExecutor):
  - На StartScreenStream(fps, maxWidth): проверь, что fps в диапазоне 1..5 и maxWidth <= 960
    (если больше/меньше — зажми до границы, не ошибку); запусти
    ScheduledExecutorService с периодом 1000/fps мс. На каждом тике: Robot.createScreenCapture
    (переиспользуй код, которым уже сжимается обычный screenshot — та же даунскейл-до-ширины
    + JPEG логика, что в screenshot(), только ширина берётся из maxWidth, а не фиксированного
    1280), отправь ScreenFrame(requestId = ID_ЭТОЙ_СЕССИИ_СТРИМА, format=JPEG, base64=...,
    width, height, seq = порядковый номер начиная с 0) через callback из A2.
  - Жёсткий предел: автоостановка через 10 минут непрерывного стрима (защита от «забыл
    выключить» — сажает батарею и трафик). Одновременно может идти только ОДИН стрим:
    если пришёл повторный StartScreenStream — сначала останови старый.
  - Тот же «агент занят», что уже используется для agent_task (найди этот механизм в
    CommandExecutor — там уже есть проверка «повторный agent_task во время выполнения ->
    ERROR "агент занят"», используй тот же принцип: пока идёт стрим, agent_task занят, и
    наоборот, если технически это удобнее всего сделать через общий флаг).
  - На StopScreenStream (или отключении сокета/остановке агента) — останови executor.

A4. CommandExecutor: case Command.StartScreenStream c -> streamer.start(...); case
  Command.StopScreenStream c -> streamer.stop() (оба — просто CommandResult OK, кадры летят
  из ScreenStreamer отдельно, не как возврат execute()).

## Часть Б — пробуждение: агент отдаёт свой MAC в QR

A5. LanAddress.java: у record Candidate добавь поле mac (String, может быть null — не у всех
  интерфейсов доступен hardware-адрес, например у Tailscale). В discover(), там где уже есть
  NetworkInterface ni для кандидата, возьми ni.getHardwareAddress() и если не null — сформируй
  строку вида "AA:BB:CC:DD:EE:FF" (каждый байт в HEX через ':').

A6. PairPhoneDialog.java: buildPayload(code, relayUrl, computerName) — добавь четвёртый
  параметр mac (nullable) и, если не null, допиши &mac=<mac> к строке (как уже сделано для
  relay/name через encode(...)). AddressOption (сейчас label+relayUrl) — добавь туда же mac
  выбранного кандидата, чтобы renderQr() мог передать его в buildPayload при выборе конкретного
  адреса (Tailscale-кандидат обычно без mac — тогда просто не дописывай параметр).

Проверка: «покажи экран» (или отдельная кнопка в приложении из следующего промпта) — на
телефон начинают идти кадры один за другим, не только один; через ~10 минут стрим сам
остановится; QR в окне «Привязать телефон» теперь содержит &mac=... для обычного Wi-Fi/
Ethernet адаптера (можно проверить, отсканировав QR любым сторонним сканером и посмотрев
текст).
```

## Промпт 3 — ПРИЛОЖЕНИЕ (`C:\diplom\jarvis\androidApp`)

```
[Общий контекст]

Задача: экран живого просмотра + кнопка «разбудить ПК». Автор новичок в Compose — объясняй
composable, State, ViewModel, корутины по ходу. Протокол уже синхронизирован с релеем и
агентом (см. их промпты): Command.StartScreenStream(fps,maxWidth)/StopScreenStream(),

## Часть А — живой экран

P1. ChatViewModel.handle(): сейчас ЛЮБОЙ ScreenFrame добавляется в чат как сообщение со
  скриншотом. Раздели по msg.seq: seq == null — как раньше (одиночный скриншот в чат);
  seq != null — НЕ добавлять в чат (иначе при 2-5 кадрах в секунду чат мгновенно забьётся),
  а класть в новый StateFlow, например _liveFrame (MutableStateFlow<ScreenFrame?>), который
  будет читать новый экран.

P2. ChatViewModel: добавь метод для отправки НЕ текстовой команды напрямую (сейчас есть только
  send(text: String), которая всегда шлёт NaturalLanguage) — например
  fun sendCommand(command: Command) { client.send(CommandRequest(UUID.randomUUID().toString(),
  command)) }. Через него из нового экрана будут уходить StartScreenStream/StopScreenStream.

P3. Новый экран «Экран ПК» (новый файл ScreenViewScreen.kt) + маленький ScreenViewModel
  (или можно обойтись без отдельной VM и читать chatVm.liveFrame — выбери, что проще объяснить
  новичку, но не дублируй состояние). Открывается по кнопке из чата (иконка рядом с
  🖥/⚙, например 🖵). На входе — chatVm.sendCommand(StartScreenStream(fps = 3, maxWidth = 800)).
  Пока кадров нет — надпись «подключаюсь…». Как только msg.seq != null начали приходить —
  показывать base64 как Image (декодировать как обычно для скриншотов, этот код уже есть в
  чате — переиспользуй). При выходе с экрана (DisposableEffect / onDispose) —
  chatVm.sendCommand(StopScreenStream()) — не оставлять стрим висеть в фоне.

P4. (Необязательный, но красивый шаг — сделай, если предыдущие пункты дались легко) тап по
  изображению -> Click(x, y): зная реальные width/height кадра (msg.width/msg.height) и размер
  Image на экране телефона (через Modifier.onGloballyPositioned или BoxWithConstraints),
  пересчитай координаты тапа в координаты экрана ПК и отправь
  chatVm.sendCommand(Click(realX, realY)). Объясни пересчёт координат подробно — это
  тема, которую стоит описать и в дипломе (raw pixel mapping).

## Часть Б — пробуждение

P5. PairingQr.kt: добавь поле mac: String? = null в PairingQrPayload, читай его из
  uri.getQueryParameter("mac") — по аналогии с relayUrl/nameHint.

P6. DeviceRepository.kt: добавь val mac: String? = null в PairedDevice (значение по умолчанию
  — старые сохранённые устройства без этого поля так и останутся читаемыми, kotlinx.serialization
  подставит null).

P7. DevicesViewModel: в pairByQr(raw) уже есть payload = PairingQr.parse(raw) — прокинь
  payload.mac дальше в pair(code, relayOverride) (добавь параметр mac: String? = null) и, когда
  outcome — PairOutcome.Success, сохрани не outcome.device, а outcome.device.copy(mac = mac).
  Для pairByCode (ручной ввод без QR) mac остаётся null — это ожидаемо, кнопка «разбудить»
  для таких устройств будет неактивна.

P8. Новый файл WakeOnLan.kt: fun sendMagicPacket(mac: String) — строит magic-пакет (6 байт
  0xFF, затем 16 раз 6 байт MAC — распарси mac, убрав ':', по 2 hex-символа на байт),
  отправляет через DatagramSocket().apply { broadcast = true } на
  InetAddress.getByName("255.255.255.255"), порт 9. Новых прав в манифесте не нужно —
  INTERNET уже есть (для широковещательной ОТПРАВКИ CHANGE_WIFI_MULTICAST_STATE не требуется,
  это разрешение для приёма multicast). Вызывать на Dispatchers.IO (сеть не в UI-потоке).

P9. DevicesScreen.kt, DeviceRow: добавь IconButton "🔌" — виден/активен только когда
  ui.device.mac != null; по нажатию — scope.launch(Dispatchers.IO) { WakeOnLan.sendMagicPacket(mac) }
  и снэкбар/тост «Отправлено. Если телефон в той же Wi-Fi, а ПК подключён кабелем — проснётся
  за ~20 секунд». Если mac == null — можно показать вместо кнопки маленькую подсказку
  «привяжите заново по QR, чтобы включить пробуждение».

Проверка: открыть «Экран ПК» — видно, как картинка обновляется несколько раз в секунду, выход
с экрана останавливает стрим (в логе агента видно, что ScheduledExecutorService остановлен);
тап по экрану кликает в нужном месте (если делал P4); усыпить ПК (кабель Ethernet, галочка
Wake on Magic Packet уже включена по прошлому исследованию), нажать 🔌 на телефоне в домашней
Wi-Fi — ПК просыпается.
```

## Финальная проверка шага

| # | Действие | Ожидание |
|---|---|---|
| 1 | Открыть «Экран ПК» в чате | Кадры идут один за другим, не единичный скриншот |
| 2 | Продержать стрим 30–60 с, выйти с экрана | Кадры перестают идти, агент в логе пишет об остановке |
| 3 | Подождать 10 минут со стримом (или сократи лимит на время теста) | Стрим останавливается сам |
| 4 | Тап по «Экрану ПК» (если сделан P4) | Курсор/клик на ПК попадает туда же, куда тапнули на телефоне |
| 5 | Привязать телефон заново по QR (после A5/A6) | В списке устройств у ПК появляется MAC (проверить логом/отладкой) |
| 6 | Усыпить ПК (Ethernet, Wake on Magic Packet включён), нажать 🔌 на телефоне в домашней Wi-Fi | ПК просыпается за ~20 с |
| 7 | Нажать 🔌 для ПК без MAC (например привязанного давно, без перепривязки) | Кнопка неактивна / подсказка привязать заново |

**После этого шага** возвращаемся к отложенной научной части
(`docs\STEP_EVAL_AND_FEATURES_PROMPTS.md`) — она никуда не делась, просто ждёт своей очереди.
