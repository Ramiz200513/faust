# Jarvis — следующий шаг: научная часть (замеры для диплома)

Как пользоваться: **«Общий контекст»** + промпт своего подпроекта — каждому ИИ-агенту.
Порядок: **Релей → Агент**. Приложение в этом шаге не трогаем (см. промпт 3).
Датасет фраз (`eval/phrases_ru.csv`, 110 штук) уже готов — положи его в `C:\diplom\jarvis-relay\eval\`,
если он там ещё не лежит.

Цель шага: получить из проекта **цифры** для главы «Экспериментальная оценка» —
точность распознавания намерений (LLM против regex) и success rate агента на реальных задачах.

---

## Общий контекст (вставлять в начало КАЖДОГО промпта)

```
Проект Jarvis — AI-агент для автоматизации многоэтапных пользовательских задач (дипломная,
тема A8). Автор учится: объясняй код по ходу, по-русски, маленькими проверяемыми шагами,
после каждого шага — как проверить.

Архитектура (Windows 11), всё уже работает end-to-end:
  Телефон (KMP/Compose) <--WS--> Релей (Spring Boot, Docker) <--WS--> Агент (Java, трей)
  C:\diplom\jarvis          — :shared (протокол) + :androidApp
  C:\diplom\jarvis-relay    — релей + PostgreSQL, docker compose, секреты в .env
  C:\diplom\jarvis-agent    — агент: трей, автозапуск, привязка по QR

ИНВАРИАНТЫ (не ломать):
 1. Протокол WebSocket меняется синхронно в 3 местах (Kotlin :shared, Java релей, Java
    агент). В ЭТОМ шаге протокол НЕ меняем — вся работа через REST-эндпоинты.
 2. CommandWhitelist — граница безопасности, не трогать.
 3. Ключ LLM только в .env релея, не логировать.
 4. Функции для ОЦЕНКИ (эндпоинты /api/eval/...) должны быть ПОЛНОСТЬЮ ОТДЕЛЬНЫ от
    продакшен-пути: реальные команды с телефона через них не идут, в audit_log эти
    вызовы не попадают — только в отдельные таблицы/файлы для замеров.

ТЕКУЩЕЕ СОСТОЯНИЕ (важно):
- AI-ядро включено и работает на Gemini (gemini-2.5-flash, ключ в .env релея).
  GeminiIntentParser разбирает фразы, StubIntentParser — резервный regex-разбор.
  intent_log (таблица) пишет каждую фразу: parser (llm|stub), command_type, latency_ms,
  whitelisted. GET /api/intent-log?format=csv — выгрузка.
- Vision-агент (agent_task) работает через LLM-прокси релея (агент не хранит ключ сам).
  Journal каждого запуска agent_task пишется в $HOME\.jarvis-agent\runs\<дата>-<id>.jsonl.
- open_app и set_volume — настоящие команды (не заглушки).
- Датасет фраз для оценки: eval/phrases_ru.csv — колонки id, phrase, expected_type
  (одно из: set_volume, open_url, open_app, screenshot, lock_screen, list_processes,
  kill_process, agent_task, unknown), notes.
```

## Промпт 1 — РЕЛЕЙ (`C:\diplom\jarvis-relay`)

```
[Общий контекст]

Задача: эндпоинт, который прогоняет датасет фраз через оба парсера (LLM и regex) НАПРЯМУЮ
(не через WebSocket, не как настоящие команды) и считает точность каждого. Плюс история
прогонов — чтобы было что показать в таблице диплома.

E1. Таблица eval_runs: id, occurred_at, parser (llm|stub), dataset_size, correct,
  accuracy (correct/dataset_size), avg_latency_ms, errors_json (не более 20 первых
  ошибок: phrase, expected, got — для разбора в тексте диплома, не для всех 110).

E2. POST /api/eval/intents (заголовок X-Admin-Token).
  Тело: CSV в теле запроса (Content-Type text/csv) с колонками id,phrase,expected_type
  (как в eval/phrases_ru.csv — если формат отличается, подстрой под реальный файл, но
  не меняй уже готовый датасет).
  Логика: прочитать все строки; для КАЖДОЙ фразы вызвать ОТДЕЛЬНО GeminiIntentParser
  и ОТДЕЛЬНО StubIntentParser (оба уже есть как бины — внедри через конструктор), замерить
  latency каждого вызова; command == null трактовать как got_type="unknown"; сравнить
  command.name() (или "unknown") с expected_type.
  Посчитать по каждому парсеру: accuracy, avg_latency_ms, и confusion-таблицу
  (expected_type -> {got_type -> count}) — она нужна для диплома, чтобы показать НЕ просто
  "точность 82%", а "чаще всего путает set_volume с unknown".
  Сохранить одну строку eval_runs НА КАЖДЫЙ парсер, вернуть оба отчёта в JSON.
  ВАЖНО: эти вызовы НЕ пишут в intent_log и НЕ пишут в audit_log — это отдельный контур.

E3. GET /api/eval/runs?format=csv (X-Admin-Token) — история прогонов eval_runs для Excel.

E4. Ограничения: датасет не больше 500 строк за раз, таймаут на весь прогон 5 минут
  (Gemini вызывается 110+ раз последовательно — предупреди в логе, что это займёт
  несколько минут и потратит квоту).

E5. Тесты: подмени оба парсера моками — проверь, что accuracy и confusion-таблица считаются
  правильно на маленьком выдуманном наборе из 5 фраз.

Проверка: положить eval/phrases_ru.csv в тело POST /api/eval/intents (например через
Invoke-RestMethod -InFile) -> в ответе видно accuracy для llm и для stub отдельно;
GET /api/eval/runs?format=csv открывается в Excel.
```

## Промпт 2 — АГЕНТ (`C:\diplom\jarvis-agent`)

```
[Общий контекст]

Задача: прогнать заранее заданный набор многошаговых задач без телефона (batch-режим) и
собрать success rate, число шагов, задержку — для той же главы диплома. Полной
автоматической проверки "успеха" не будет: содержательно оценить, выполнилась ли задача,
может только человек, глядя на итоговый скриншот. Это нормально для такой оценки — не
пытайся угадывать успех эвристиками.

B1. Файл сценариев eval\agent-tasks.json рядом с проектом (создай, если нет — 15-20 задач
  РАЗНОЙ сложности, например: {"id":1,"goal":"открой википедию","scope":"browser",
  "maxSteps":5}, ... до задач в 10-15 шагов вроде "найди на ютубе видео про X и открой
  первое"). Придумай реалистичный набор вместе с автором на основе того, что уже
  обсуждали (примеры были в этом чате и в STEP_AI_CORE_PROMPTS.md).

B2. Флаг запуска --eval-tasks eval\agent-tasks.json:
  - агент НЕ поднимает трей и НЕ ждёт команд с телефона;
  - выполняет задачи по очереди (agent_task как обычно, через тот же CommandExecutor);
  - между задачами пауза 5 с (не долбить Gemini квотой без перерыва);
  - как и раньше, каждый запуск пишет journal в runs\<дата>-<id>.jsonl (ничего не менять
    в этом формате — берём готовое);
  - ПОСЛЕ всех задач — сводка runs\summary.csv: task_id, goal, steps_used, elapsed_ms,
    finished_reason (ok/error/timeout), screenshot_path (последний скриншот задачи,
    сохранить рядом в runs\screenshots\<id>.jpg), и ПУСТАЯ колонка success — её автор
    проставит сам руками (0/1), глядя на скриншоты. Объясни в комментарии в коде, почему
    это делается руками, а не автоматически.

B3. Консольный вывод по ходу прогона: "[3/18] найди на ютубе... — 7 шагов, 11.2 с" —
  чтобы было видно прогресс на длинном прогоне.

Проверка: java -jar agent.jar --eval-tasks eval\agent-tasks.json (или через gradlew run
--args) -> в конце runs\summary.csv со всеми задачами и пустой колонкой success;
в runs\screenshots\ лежат картинки.
```

## После того как оба прогона сделаны

1. **Точность разбора фраз**: `GET /api/eval/runs?format=csv` из релея — сразу таблица
   LLM vs regex (accuracy, средняя задержка) для диплома.
2. **Success rate агента**: открой `runs\summary.csv`, руками проставь `success` (0/1) по
   скриншотам, посчитай долю успешных, среднее число шагов, среднюю задержку — отдельно
   по простым задачам (≤5 шагов) и сложным (>5 шагов). Разница между ними — тоже
   содержательный результат для диплома (подтверждает наблюдение про накопление ошибки
   по шагам, которое обсуждали).
3. Присылай мне оба CSV (intent-eval и summary с проставленным success) — соберём из них
   таблицы и графики для главы «Экспериментальная оценка» (skill xlsx/dataviz).
